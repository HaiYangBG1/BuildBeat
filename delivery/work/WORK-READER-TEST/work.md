# 读者测试：让一个没上下文的 AI 只读这份文档，看它读出了什么、读不出什么

## 目标

BuildBeat 往项目里放的 work.md 和 result.md，是写给以后接手的人和会话看的。到现在为止，所有检查都在管"写对没有"（摘要对不对、链接在不在、写回行核不核得上），没有一样在管"别人读不读得懂"。

做完后多一条命令：把一份 work.md 或 result.md 交给一个没有任何上下文的只读 AI，只给它这一份文档，让它回答一组固定的问题。结果有三样：

- 它读出来的答案，几行字。所有者接受工作说明前看这几行，比读完整份文档快，也能看出文档有没有把意思说对。
- 它答不出、只能猜的地方。这是写的人该补的。
- 能和 Git、记录对上的答案，由运行时核对，标出对错。

每次结果连同文档的字节数记在工作文件夹里，绑定文档当时的摘要。同样读得出来，越短越好。

## 起因

2026-11-10 所有者看过独立审视的结论后说：「冷读测验很好」，并改叫读者测试：「本质是想把work.md做扎实，也是别人看来【往别人的仓库放几百个过程文件】这件事变的没那么糟糕，这些文件变的真的有价值」。当时会话补充、所有者没有反对的三点：篇幅要算进去；已关的工作只拿 result.md 去测；标准答案来自记录和 Git，不来自文档自己。

2026-11-11 所有者在 WORK-CLEAN-START 关窗后说：「起草读者测试」。

## 已核实的现状（2026-11-11，`7964cf1`）

**已确认**

- 本仓现有 26 份 work.md，共 216 KB，平均 8.3 KB；40 份 result.md，共 66 KB，平均 1.6 KB（当天 `wc -c delivery/work/*/work.md` 和 `result.md`）。没有任何记录说明这些文档被别人读懂过。
- 运行时现在只认两个角色：`src/v2/cli/review-config.js:28` 是 `["verifier", "reviewer"]`，配置里写别的角色会报 `unknown key`（同文件 171-172 行）。
- 随包的 `templates/v2/envelope/worker.sh:19-21` 只接受 `reviewer` 角色，别的退出 64。
- 审查者拿到的输入里有工作说明的路径和摘要（`src/v2/runtime/orchestrator.js:221`），它在这个提交的检出里运行，看得到整个仓库。读者测试要的正相反：只看得到一份文档。
- 能当标准答案的事实，运行时已经会算：一项工作改过哪些文件（`src/v2/runtime/work-commits.js:140` 的 `codeCommitsOf`）；result.md 的写回行（`src/v2/runtime/closeout.js:134` 的 `parsePromotions`）；工作之间的关系行（`src/v2/runtime/threads.js:24` 的 `parseLinks`）；被批准的提交在 `delivery/work/<ID>/decisions.jsonl` 里。
- `src` 现在 7,985 行（`find src -name '*.js' | xargs cat | wc -l`）。
- 本机全局装的 `buildbeat` 是 5.5.0，不认识这个分支上的新命令；这项工作要用仓库里的 `node bin/buildbeat.js` 送审。

**待核**

- 审查用的 AI 命令行工具放在一个空目录里运行、文档从提示词里给，它会不会仍然去翻别的目录。实现时用真实工具跑一次，看它的输出。运行时拦不住工具读文件，只能不把仓库给它。
- 一次读者测试用多久、多少钱。实现后在本仓的文档上实测，写进 result.md。

## 范围

做：

- 一条新命令和它的记录文件。
- 项目配置里多一个可选角色 `reader`，随包多一份读者提示词，`worker.sh` 认这个角色。
- `status --work <ID>` 多一行读者测试的结果；`accept` 在当前这份 work.md 没测过时提醒一行，不拦。
- 在本仓挑 10 份文档用真实工具测一遍，结果写进 result.md，作为第一份"读"的数据。
- Skill 和指南里各加几句：什么时候测、结果怎么看。

不做：

- 不打总分，不排名，不设及格线。
- 不自动改文档。读者答不出的地方由写的人决定补不补。
- 不拦接受、不拦关窗。
- 不读试点仓。不发版、不推送。

## 开工前待拍板

接受本说明即按「推荐」执行；要改哪项直接说，改完表再接受。

| # | 问题 | 推荐 | 另一种做法与后果 |
|---|---|---|---|
| 1 | 命令叫什么 | `buildbeat reader --repo <path> --work <ID> [--doc work\|result]`。不写 `--doc` 时：有 result.md 就测它，没有就测 work.md | 叫 `quiz` 或 `read-test`：前者像玩笑，后者和 `review` 的写法不一致 |
| 2 | 给读者看什么 | 只给这一份文档的正文，放在提示词里；读者在一个新建的空目录里运行，仓库不给它 | 让它在仓库检出里运行：它会去翻代码把答案查出来，测的就不是文档了 |
| 3 | 问哪些问题 | 固定两组，不能配置，原文见表下 | 让项目自己配问题：每个项目的结果就没法互相比，也多一处要学的配置 |
| 4 | 哪些答案由机器核对 | 只核对有独立事实的三项：work.md 的"要改哪些目录或文件"对照这项工作的提交实际改过的路径（还没有提交时对照配置里的 `allowedPaths`，两样都没有就不核对）；result.md 的"在哪个提交"对照记录里被批准的提交；result.md 的"写进了哪些文档"对照写回行核对通过的路径。其余答案原样给人看 | 再请一个 AI 给答案打分：多一次调用，分数本身又要人信 |
| 5 | 结果记在哪 | `delivery/work/<ID>/reader-tests.jsonl`，一次一行：时间、测的是哪份文档、文档摘要和字节数、每个问题的答案、答不出的清单、核对结果。不建运行，不进台账 | 当成一轮运行记进台账：台账格式是冻结的，为它加事件类型不值得 |
| 6 | 用哪个 AI | 配置里写了 `workers.reader` 就用它；没写就用 `workers.reviewer` 的命令配读者的提示词 `prompts/reader.md`。`worker.sh` 多认一个 `reader` 角色，行为和 `reviewer` 一样 | 必须单独配：每个项目多配一段，多数项目用的是同一个工具 |
| 7 | 要不要拦 | 不拦。`accept` 发现当前这份 work.md 没测过时打印 `note: delivery/work/<ID>/work.md has no reader test; buildbeat reader --repo <path> --work <ID>`；`status --work <ID>` 显示 `reader: work.md · answered <n>/<m> · unanswered <k> · checked <a>/<b> · <KB> KB`，文档改过后显示 `reader: work.md changed since its reader test` | 没测过不许接受：读者工具出问题时所有工作都卡住 |
| 8 | 工具出问题怎么办 | 超时、崩溃、exit 75、没交答案或答案读不懂：打印原因，退出码 1，不写记录 | 记一行失败：记录里混进不是文档问题的行 |
| 9 | 代码规模和止损线 | `src` 不超过 8,400 行。这项工作的审查上限 6 轮 | 不设线：减法刚做完，下一项就把它加回去 |

第 3 项的问题原文。读者按编号用 JSON 回答，每个答案是一段短文字或一个列表，答不出的写进最后一问：

work.md：

1. 做完后别人能看到什么？一句话。
2. 要改哪些目录或文件？
3. 哪些东西明确不动？
4. 用什么命令或观察判断做完了？
5. 开工前还有哪些事要人定？
6. 遇到什么情况必须停下问人？
7. 读完这份文档，还有什么是你不知道、只能猜的？

result.md：

1. 做成了什么？在哪个提交或版本？
2. 定了哪些以后要遵守的事？
3. 剩下什么？转去了哪里？
4. 写进了项目哪些文档？
5. 读完这份文档，还有什么是你不知道、只能猜的？

## 验收

机器检查，过全套门禁：`npm test`、`npm run check:docs`、`npm run test:envelope`、`npm run test:plugin`、`npm run test:pack-firstrun`、`npm run pack:check`。另外：

- 夹具仓里用脚本化的读者走通：测 work.md、测 result.md、记录写出一行、`status --work` 显示结果、文档改一个字后显示已变、`accept` 的提醒出现和消失。
- 脚本化的读者能看到的只有提示词里的文档：它运行的目录是空的，不在仓库里。
- 三项核对各有对和错两种情况的测试；没有独立事实时显示为没核对，不算错。
- 读者超时、崩溃、交回读不懂的答案：退出码 1，记录文件没有新行。
- 配置里写 `workers.reader` 和不写两种情况都走通；`worker.sh reader` 的壳测试通过。
- `find src -name '*.js' | xargs cat | wc -l` 不超过 8,400。

由人确认：

- 本仓 10 份文档（5 份 work.md、5 份 result.md，长短各半）用真实工具测出来的结果表：每份的字节数、答出几问、答不出什么、核对对了几项。所有者看这张表判断这个测试有没有用。
- 合并决定。

## 实施计划

1. 读者提示词、`worker.sh` 的 `reader` 角色、配置里的可选角色。
2. `reader` 命令：取文档、在空目录里跑读者、解析答案、核对三项、写记录。
3. `status --work` 的一行和 `accept` 的提醒。
4. 测试；Skill 和指南各加几句；CHANGELOG 的未发布条目加一条。
5. 用仓库里的 `node bin/buildbeat.js review` 送审，修到通过，停在合并决定。
6. 合并后在本仓 10 份文档上实测，结果表写进 result.md。

## 停止条件

- 真实工具在空目录里仍然读到了仓库内容，测出来的不是文档。
- 实测发现读者的答案在同一份文档上两次差别很大，结果不可比。
- 三项核对里有一项的独立事实其实取不到，或取到的和文档是同一个来源。
- `src` 要超过 8,400 行才做得完。
- 要改台账格式，或要改接受、批准、关窗的检查。
