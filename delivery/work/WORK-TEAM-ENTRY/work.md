# 只用 Skill 和项目文件，也是正式用法

## 目标

所有者把 BuildBeat 推荐给团队时，同事最先看到的是"装 Node 20、全局装运行时"。可同事要的首先是把需求的上下文留在项目里：为什么做、查实了什么、定了什么、做成了什么。这些现在全是纯文本，AI 照着写就行，不需要运行时：work.md 的八节、result.md、关系行、`Work:` 标记、带指针的现状。运行时多给的是自动实现、验证、审查、修复的循环，以及对这些记录的核对。

本 Work 把"只用 Skill 和项目文件"写成和"装运行时"并列的一种完整用法，作为推荐同事起步的入口：
- 告诉同事怎么开始；
- 说清能得到什么、少了什么；
- 说明以后什么时候、怎么加上运行时。

## 起因

10-24 方向讨论里提过：团队入口跟第 1 件一起做，只用 Skill、work.md 和结果页、不装运行时，应该算正式用法。现在的指南 12 把它写成了兜底。前几件做完后，所有者 2026-10-25 问到哪了，我答"团队入口还差一半"；所有者说：「先做完，再说合并的事」。

## 已核实的现状（2026-10-25，main `61a7f3b`）

**代码已确认**

- README 的"开始用"只有一条路：复制一段话给 AI，让它装 Node 20 和全局运行时（`README.md:37-68`）；用 Claude Code 的可以装插件，但插件说明写着运行时要另装（`plugins/buildbeat/.claude-plugin/plugin.json`）。
- Skill 开头的承诺写着"执行需要本地 `buildbeat` 运行时"（`SKILL.md:8`）；没有运行时只占一条，限定为"只读状态、写 work.md 和规定格式的决定行"（`SKILL.md:17`）。
- 指南 12（`docs/v2/guide/12-without-runtime.md`）作为手册是全的：可以读什么、可以写什么（接受行、裁决行、result.md、关窗行、关系行、现状、`Work:` 标记）、不得做什么。但它的标题是"不装运行时也能参与"，最后一节是"交给装有运行时的一方"，前提是团队里总有人装了运行时。
- 能力矩阵开头写着只有一条产品路径："Skill → local runtime → project records"（`docs/CAPABILITY-MATRIX.md:3-8`）。
- 插件把 SKILL.md、文档和模板一起带上（`plugins/buildbeat/`），所以用 Claude Code 的同事装上插件，不装 npm 包也能拿到模板和指南。
- 手写记录的格式和运行时之间有测试约束：中英两版的 JSON 示例必须一致（`tests/check_docs.py:791-810`）；照指南 12 手写的接受行和关窗行，运行时必须认（`tests/v2-screenshot-release.test.js:392-430`）。

  - 最后一节改成"以后加上运行时"：什么时候值得装、装上后已有记录照常生效。
  - 文件名不变，已有链接不断。
- **Skill**：开头的承诺改成"自动推进需要运行时；没有运行时也能用项目文件把上下文完整记下来"。"没有运行时"那条展开，写清文件模式下会话自己做什么：
  - 起草 work.md，按用户的决定手写接受行，算好摘要；
  - 写 result.md 和关窗行；
  - 提交带 `Work:`，写关系行；
  - 现状写指针，用 `git diff` 自查变没变；
  - 不说验证、审查或核对已通过。
- **README**（中英）：在"开始用"下加一句，不想装 Node 或运行时，只用 Skill 和项目文件也行，链到指南 12。别的不动。
- **索引和矩阵**：指南目录（中英）、能力矩阵开头、迁移说明里的链接文字改成新标题；能力矩阵写明有两条路径。
- CHANGELOG 新增条目。

不包含：

- 运行时代码；不装运行时也能核对手写记录的工具（等真有同事写错再说）。
- 插件清单和市场描述（`plugin.json`、`marketplace.json`）里"运行时另装"的说法，改它们牵涉插件版本号，另外处理。
- README 的其他部分、GitHub About。
- 试点工作区的迁移、发版、推送。
