# 已核实的现状带上代码指针，代码变了能看出来

## 目标

work.md 里"已核实的现状"写的是开工前查实的事，比如某个文件第几行怎么写、某个开关默认是什么。它只在写下的那一刻成立。工作搁几天才开跑、交给别人接手、或者另一项工作先合进去改了同一段代码，这些事实可能已经不对了，但读的人看不出来，只能整段重查，或者冒险照着旧事实动手。

本 Work 让运行时替人看一眼：现状里引用的代码位置，从核实时的提交到现在有没有被改过，改了的列出来。这样"回来能信"就从测试结果延伸到了上下文本身。

## 起因

所有者 2026-10-25：「起草第 4 件剩下那半的 work.md：已核实的事实带证据指针，运行时能指出哪些事实所指的代码已经变了。」这是 10-24 方向讨论里第 4 件的后一半，前一半（从一行代码找回工作）已由 WORK-CODE-TRACE 完成。

- related: WORK-CODE-TRACE
- related: WORK-CONTEXT-CLOSEOUT

WORK-CONTEXT-CLOSEOUT 把"已核实的现状（日期，在哪个提交上）"写进了模板，但运行时从不读它。

## 已核实的现状（2026-10-25，main `e863477`）

**代码已确认**

- 运行时不读 work.md 的任何章节。只有关系行（`threads.js`）、result.md 的写回行和摘要（`closeout.js`）是按行读的，都走共用读法 `textLines`（`src/v2/runtime/closeout.js`）。
- 模板 `templates/v2/work.example.md` 的节标题是 `## Facts checked (<date>, on <commit>)`，要求已确认的每条带出处；SKILL.md 写的是"标日期或提交"，提交不是必填。
- `accept` 和 `check` 已有打印提醒的位置（`src/v2/cli/run.js` 的 `commandAccept` 与 `commandDoctor`，目前提醒 `delivery/` 被忽略）。`status --work` 有给单项工作加块的钩子（`renderOverview` 的 `extra`，现在挂的是关系线 `renderThread`）。
- Run 开始时先把起点钉成一个提交（`commandStart`），运行记录里存为 `workspaces.<RUN>.base`。

**试点工作区和本仓（只读统计，2026-10-25）**

- 114 份工作说明里，31 份有"已核实的现状"一节：21 份标了日期，13 份钉了提交，6 份都没标。
- 引用代码的方式几乎都是在反引号里写路径，85 处带行号，写成"路径:起-止"。约一半只写路径后半段（从模块目录写起），在那个提交里能唯一对上一个文件。反引号里还有很多不是文件的名字（方法名、配置键）。
- 核实和开跑隔得很近：18 项能对上日期的工作，16 项在核实当天开始第一轮 Run，2 项隔一两天。
- 钉了提交、指针对得上文件的有 11 项工作。开跑前，它们引用的代码行一处都没变，只有 1 项引用的文件在别处改过。
- 也就是说，试点里还没出过"开跑前现状已经变了"的事。价值在以后：工作写好先放着、交给同事接手、或者被别的工作抢先改了同一段代码。
- 这 11 项工作带行号的指针里，后来文件有改动的 31 处，其中 12 处改的是别的行，引用的那几行没动。

## 范围

包含：

- **写法**：在节标题里写一个本仓存在的提交（模板已是 `Facts checked (<date>, on <commit>)`），节内用反引号写 `路径` 或 `路径:行` / `路径:行-行`。运行时不认章节名，只认"标题里写了本仓存在的提交"的那一节，中英文标题都行。路径可以从仓根写，也可以只写后半段，在那个提交里只对上一个文件就算。反引号里的目录名和不是文件的名字（方法名、配置键）不当指针；带 `/` 或行号却对不上文件的，列为找不到。代码块和 HTML 注释里的不算，沿用 `textLines`。
- **运行时**：
  - 解析指针，按第 2 项选对比的提交，按第 3 项判断变没变；改了的附上改动它的提交数和最近一个提交。
  - `status --work` 对没关的工作加一块"现状"，列出变了的、找不到的；`--json` 带上同样的字段。
  - `accept` 和 `check` 有变了的指针时各打印一行提醒，不拦（第 4 项）。
- **模板**：`work.example.md` 的这一节写明指针格式，以及标题里的提交是对比的起点。
- **Skill**：起草时在标题里钉提交、按格式写指针；开跑前、接手时先看 `status --work` 的现状块，变了的重新核实，改 work.md 后重新接受；从别的工作抄来的现状只当线索，重查后钉自己的提交。
- **文档**（中英各一份）：快速开始（写现状）、接续（接手先看现状块）、不装运行时也能参与（指针是纯文本，可以手写）、能力矩阵；CHANGELOG 新增条目。
- 回归测试；安装清单按需更新。

不包含：

- 指向别的仓的文件（主仓的工作引用代码仓）。只在放 work.md 的仓里找，找不到的列为"找不到"。按"记录直接放进项目"的规则迁移后，这种情况会变少。
- 不是代码的事实：生产状态、命令输出、外部接口返回。它们没有可比对的提交。
- 函数或符号级别的比对（只比行，不认"这个函数还在不在"）。
- "待核"那一类事实的跟踪。
- 跨仓总览里显示现状，以及 `history --path` 的输出里显示现状。
- 给已有的工作补提交号。
- 发布、推送、版本号。

## 开工前待拍板

接受本说明即按"推荐"执行；要改哪项直接说，改完表再接受。

| # | 问题 | 推荐 | 另一种做法与后果 |
|---|---|---|---|
| 1 | 指针怎么写 | 提交写在节标题里，节内用反引号写 `路径[:行[-行]]`；路径能写后半段，唯一对上就算。和试点现在的写法一致，照现在的习惯写就能查 | 每条事实自己写 `路径:行 @ 提交`，像 result.md 的写回行：不依赖标题，但现有写法都对不上，每行还要重复提交号 |
| 2 | 跟什么比 | 还没开跑的比当前 HEAD（`check` 比 run 配置里的起点，默认也是 HEAD）；开过跑的比最近一轮 Run 的起点；已关的不查，因为现状本来就是开工前的样子，做完后什么成立由 result.md 说 | 一律比当前 HEAD，已关的也查：从代码追到旧工作时也能看出哪些变了，但几乎每条都会因为这项工作自己的改动显示"变了" |
| 3 | 怎样算变了 | 写了行号的，只看这几行有没有被改（按核实时那个提交里的行号算）；文件别处改了单独计数，不提醒。没写行号的，文件有任何改动就算。文件删了或挪走算"找不到" | 一律按文件算：更简单，但试点里约四成"文件变了"其实没动到引用的行，都会变成提醒 |
| 4 | 变了以后怎么办 | 提醒，不拦：`status --work` 列出来，`accept` 和 `check` 各打印一行 | `check` 和开跑时拒绝，直到重新核实（改 work.md 里的提交号并重新接受）：保证开跑前现状是新的，但试点里还没出过一次这种情况，拦了只会多一步 |

**对外名字（接受即确认）**

- 指针：节标题里的提交，加节内反引号里的 `<路径>`、`<路径>:<行>`、`<路径>:<行>-<行>`。
- `status --work` 新增的块（只给没关、且有带提交的现状一节的工作）：
  - 第一行：`  facts: checked on <commit>, compared with <against>: <n> pointers, <k> changed`，有的话再接 `, <e> changed elsewhere in the file`、`, <u> not found`。`<against>` 是 `HEAD` 或 `base of <RUN-ID>`。
  - 每个变了的：`    changed  <路径>[:<行>-<行>]  (<c> commits, latest <commit> <标题>)`
  - 每个找不到的：`    not found  <写的原文>  (<原因>)`，原因是 `no file at <commit>`、`matches <m> files at <commit>` 或 `not in <against>`
- 现状一节写了指针、标题里却没有本仓的提交时：`  facts: no commit of this repository in the heading; nothing compared`
- 提醒（`accept`、`check`）：`warning: facts in delivery/work/<ID>/work.md were checked on <commit>; <k> referenced places changed since: <路径>:<行>-<行>, <路径>; re-check them before starting`
- `--json`：`facts: {checkedOn, against, pointers: [{text, path, lines, state: "same" | "changed" | "elsewhere" | "not found", commits, latest: {commit, subject}}]}`。没有这一节的工作和已关的工作不带这个字段，输出与以前逐字一致。

## 验收

机器检查：

- `verify.sh` 全过：`npm test`、文档检查、Bash 信封、Claude 插件、安装后首跑、本工作范围内的 `git diff --check`。
- 回归测试至少覆盖：
  - 只认标题里写了本仓提交的那一节，中英文标题都行；标题里有两个提交时，取本仓存在的那个；没有本仓提交时给出上面那行说明。
  - 三种写法（`路径`、`路径:行`、`路径:行-行`）都能读出；后半段路径唯一对上算，对上多个或对不上列为找不到；目录名和不是文件的名字（方法名、配置键）不报错也不列出；代码块和 HTML 注释里的不算。
  - 引用的行被改、只改了文件别处、没写行号的文件被改、文件删了，四种情况各自判对；引用的行前面插入或删掉行（行号整体挪动）不算引用的行被改。
  - 对比的提交：没开跑的是 HEAD，开过跑的是最近一轮的起点，已关的不出现这一块。
  - `accept` 和 `check` 在有变了的指针时打印提醒、没有时不打印；`check` 用 run 配置里的起点。
  - 输出原文和 `--json` 字段；没有这一节的工作，`status --work` 的 JSON 与以前逐字一致。
- 独立只读审查没有未裁决的 P0/P1。

要人确认：

- 在试点工作区挑一项没关、钉了提交的工作跑 `status --work`，看现状块是否说对；记下耗时。

## 实施计划

1. 运行时：新模块读现状一节的提交和指针，算出对比提交、逐个判断变没变；接进 `status --work`、`accept`、`check`。
2. 模板、Skill、中英文档、CHANGELOG。
3. 回归测试和安装清单。

驾驶会话亲自写代码，以 `--adopt` 交给 Run；verify 和 review 由独立 worker 执行。

## 停止条件

- 范围要扩到"不包含"里的任何一项，先停下来问。
- 在试点后端仓，`status --work` 因为现状块多出 2 秒以上，先停下来再定做法。
- 审查轮数上限 6 轮（run-config `budgets.reviewRoundsPerWork`）。合并、推送、发布另行决定。
