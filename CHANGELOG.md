**Breaking.** The runtime records, verifies, reviews and binds the approval. It no longer writes code or drives a loop, and it reads only the current format (WORK-CLEAN-START). Finish or cancel work in progress with the version you have before installing this one.

- The session writes and commits the change. `buildbeat review --repo <path> --work <ID> [--commit <sha>]` checks that commit out by itself, runs the project's verifier on it and, when that passes, a read-only reviewer, then removes the checkout. Nothing is written, retried or repaired. A review ends `FAILED` (the commit's problem: verification failed, a path outside `allowedPaths` changed, or the verifier left the checkout dirty or moved its HEAD), `CANCELLED` (a tool's problem: timeout, crash, exit 75, no report, an unreadable report, or a reviewer that touched files), or waiting for the person's decision. A new review of the work supersedes the one still waiting; a review whose process was killed is settled as `CANCELLED` by the next. One review runs in a repository at a time.
- Decisions are made by work: `buildbeat decide --repo <path> --work <ID> --action approve --candidate <full SHA>` or `--action reject --reason <why>`; findings are ruled on with `--action accept|dismiss --fingerprint <fp>`; `--action close [--draft]` closes a work as before. An approval is refused while a P0 or P1 finding is undecided, when the commit named is not the one waiting, or when work.md is no longer the accepted one.
- The commands are `accept`, `review`, `decide`, `release`, `status`, `check`, `history` and `hooks`. `check` is `buildbeat check --repo <path> [--work <ID>]`; `release` is `buildbeat release --repo <path> --work <ID> [--env <name>] [--ref <ref>] [--note <text>]`. `run`, `stop`, `gc`, `watch`, `start`, `resume`, `overview`, `inbox`, `metrics`, `approve`, `reject`, `findings`, `doctor`, `preflight`, `events`, `replay` and `observe` are unknown commands (exit 2).
- A project has one `delivery/run-config.yaml` with `workers.verifier`, `workers.reviewer`, `envelope`, `requires`, `redact`, `release`, `requireScreenshot` and `maxReviewSeverity`. A work overrides keys in `delivery/work/<ID>/run-config.yaml`, which also takes `allowedPaths` (the work's own folder is always allowed) and `base` (default: the last commit that changed its work.md). Any other key, including `repo`, `work`, `run`, `workflow`, `riskPreset`, `entry`, `policies`, `budgets`, `cache`, `reviewTriage`, `stopAt`, `supersede`, `parallel`, `stallAfterMs`, `workers.builder` and `workers.fixer`, is an error that names the key and the file. Run ids are `RUN-<work id without WORK->-<two digits>`.
- Gone with the loop: the builder and fixer workers and their prompts, `run --adopt`, the fix loop and its convergence check, budgets, the verify cache, parallel runs, stall detection and stale-run recovery, `gc`, `metrics`, notifications, risk presets, the per-work `workflow.yaml` and the mock adapter. Findings are matched across rounds by fingerprint only (`reRaised`); the fuzzy same-issue match is gone.
- A work is its `work.md`. Works described by `intent.md` / `plan.md` are not read any more: closed ones show as closed with the first line of their result page as title, and an unclosed one shows as `LEGACY` (`legacy records: read the folder, or close it with a result.md`). Records of earlier versions are left as they are, `history --path` traces code to them as before, and the records this version writes are readable by 5.5.0. A run this version made carries `pass: true`.
- `status`: the cost line is `cost: review rounds <n> · findings <m>`. `--all-repos` looks at the main repository and its immediate sub-directories that have `delivery/work`.
- `status` calls a finding `(open)`, and counts it in `unadjudicated P0/P1 findings <n>`, only while the latest review that happened still raises it (WORK-STALE-FINDINGS). A finding nobody ruled on that a later review no longer raises shows as `(not raised again)`; a later run that never reached review changes nothing. This is what an approval already looked at: the review of the commit being approved. A work reviewed for eight rounds had listed nine fixed findings as open.
- A work must pass a release readback before closing only when its own run config declares `release:` or a readback was already recorded for it; a project-level `release:` is the default readback command. A repository that only records readbacks needs no workers in its config.
- New: the reader test (WORK-READER-TEST). `buildbeat reader --repo <path> --work <ID> [--doc work|result]` hands one document of a work, result.md when there is one and work.md otherwise, to a read-only AI that is given nothing else and runs in a new empty directory outside the project. It answers fixed questions (seven for work.md, five for result.md); the last collects what it could not tell. The runtime checks the two answers about result.md that something other than the document can confirm: the commit the reader names, against the approved commit, and the documents it names, against the write-back lines Git confirms. Answers about work.md are shown as they are. Each result is appended to `delivery/work/<ID>/reader-tests.jsonl` with the document's digest and size; `status --work` shows `reader: <doc> · answered <n>/<m> · unanswered <k> · checked <a>/<b> · <KB> KB`, or that the document changed since. Nothing is scored or blocked; `accept` reminds once when the current work.md was never tested. The reader is the optional `workers.reader`, or the reviewer's command, with the prompt `prompts/reader.md`; `worker.sh` takes the `reader` role. Tool trouble exits 1 and records nothing.
- Paths no longer carry `v2` (WORK-DROP-V2-PATHS): `templates/v2/…` is `templates/…`, `docs/v2/guide/…` is `docs/guide/…`, the ledger format is `docs/SPEC-0001-events-v1.md`, and in the repository `src/v2/` is `src/` and the tests lost their `v2-` prefix. Nothing redirects from the old paths. In a project that adopted BuildBeat, change what points at the old ones: references to `templates/v2/…` (in AGENTS.md and the like) and links to `docs/v2/guide/…` on GitHub. Development no longer happens on a `v2` branch: branches fork from `main`.
- The package: the example project, the templates (one reviewer prompt, a project config sample), the Skill and the guides describe this surface. `docs/MIGRATION.md`, `CHANGELOG-v1.md`, `docs/history/`, `docs/releases/`, the three RFCs and the milestone acceptance records are removed; `docs/SPEC-0001-events-v1.md` stays. Evals keep `reviewer-readonly`, `stale-approval`, `evidence-required` and `gate-cannot-self-pass`.
