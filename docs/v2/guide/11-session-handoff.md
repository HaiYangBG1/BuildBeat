# 跨会话接续：关掉聊天，保留工作

**简体中文** | [English](11-session-handoff.en.md)

BuildBeat 的接续依据是项目文件、Git 与运行台账。新会话读取这些事实后，判断继续执行、恢复中断、处理待批，还是开始同一 Work 的下一次 Run。接手的人可以是自己，也可以是另一位团队成员。接手不需要旧聊天全文，也不会自动保存只存在于聊天中的讨论。

## 关闭旧会话前

在当前会话中说：

> 我要换会话。把继续工作必需、但还只在聊天里的上下文落到项目文件，核对当前 Work、候选、未验证事项、待批和运行状态。

会话应完成这些核对：

- 目标、范围、验收条件与决定已有明确文件落点；补录事实时不改写既有批准，也不把未接受的想法写成已接受计划。
- 候选提交、工作树中的未提交改动、测试证据与下一步可定位；关键环境事实写入 Work 的 `env-facts.md`，秘密只标来源，不写入项目记录。
- 使用 `overview` / `inbox` / `status` 读回实况。若 Run 还在执行，说明进程是否脱离驾驶会话；无法确认就说明不确定。
- 需要跨机器或共享时，按已有授权提交、同步相关项目文件和候选分支；写到磁盘不等于已提交或已推送。

这些事实已落盘时，无需为每次换会话另写一篇长交接报告。关闭或删除聊天应只处理聊天记录，保留项目目录、运行台账与工作树；某些工具会连同临时工作区一起清理，先核对其实际范围。

## 新会话如何接手

在**同一项目目录**打开新会话，按所用工具的方式加载 BuildBeat Skill 和项目 `AGENTS.md`，然后说：

> 继续这个项目。先读 BuildBeat 入口和当前工作项，核对 Git、进度、验证结果和待批事项，再在已有授权范围内继续。

会话先读当前事实：

```bash
buildbeat overview --repo .
buildbeat inbox --repo .
```

随后读取对应 `delivery/work/<ID>/` 的目标、计划、决定和配置；需要活动 Run 细节时运行 `status --repo . --run <RUN-ID>`。ID 从实际输出读取，不凭聊天猜。

| 读到的情况 | 下一步 |
|---|---|
| Run 仍在正常执行 | 继续观察，避免启动重复 Run 或改它的工作树 |
| Run 等人决定 | 展示当前待批对象与证据；新会话不会自动继承一份不存在或已过期的批准 |
| Runner 中断，运行台账和工作树仍在 | 按恢复手册核对现场，再 `resume --config <配置路径>`；中断步可能重跑 |
| 工作树脏、配置改变、批准失效或现场缺失 | 说明具体差异，按运行时要求处理，不能声称已无损恢复 |
| Run 已终结，Work 还需后续执行 | 基于现有工件和候选准备下一次 Run；终态 Run 不重新打开 |
| 工作已经合并或发布 | 回读相应 Git 或发布事实，避免因某次旧 Run 被取消而重复执行 |

恢复批准与最终合并决定是不同动作。详见 [批准指南](07-approval-guide.md) 和 [故障恢复](10-recovery.md)。

## 另一位团队成员接手

交出方将需要共享的目标、计划、决定、验收记录和下一步落到项目文件，按已有授权同步到共享仓库，并使候选提交可达。在 Work 的项目记录中说明当前由谁继续推进、原 Run 是否仍在执行及所在环境；运行状态仍以实际回读为准。

接手方取得项目访问权限后，同步相应文件和候选分支，加载项目入口，用自己的 AI 工具核对范围、证据、待批事项与环境。仍然有效的既有决定继续保留；接手不会自动获得他人的合并、发布或凭据权限。

若原 Run 尚未终结，先核对原执行环境。新机器的 `overview` 或 `inbox` 没有活动项，不代表旧机器没有活动 Run。本地锁不会协调不同机器或 Git 副本，不能据此重复启动同一份工作。需要在新环境重新执行时，先明确原 Run 的处置，再从已同步工件与候选准备后续 Run。

团队成员可以按端到端工作包分工，也可以交接同一个包。产品、全栈、测试是各成员可调用的 AI 视角（审查是 Run 内置的只读 reviewer，不是会话视角），具体接手的人与视角可以变化。访问控制依赖已有 Git 托管、执行平台和团队授权约定，BuildBeat 不另建成员账号或权限系统。

## 换工具、模型和角色

项目工件是可读文件，可由不同工具消费。新工具需要加载入口、具备必要权限并能读到同一项目；执行 Worker 还需满足命令、鉴权与输出合同。模型由外部 AI 工具选择。

产品、全栈、测试三个视角都读同一个 Work 的目标、约束与证据，按各自写入边界接手；审查由 Run 内置的只读 reviewer 承担。换视角不改变已经接受的范围，不需要把同一套事实复制成多份进度文档。当前一仓仅支持一个活动 Run。

这说明协议如何接续，不代表任意工具组合都已通过真实接力验证。已有工具证据见 [能力矩阵](../../CAPABILITY-MATRIX.md)，接入要求见 [Adapter 指南](04-adapter-guide.md)。

## 换机器与运行恢复的区别

| 保留或同步的内容 | 能支撑什么 | 不能直接推出什么 |
|---|---|---|
| 已提交的 Work、决定、规范与终态记录 | 新机器读取长期项目事实 | 原始运行日志与活动检查点也已同步 |
| 候选分支及其提交 | 读取候选代码，核对差异与合并状态 | 普通 clone 已取到仅存在于旧机器上的分支 |
| 本机 runtime 与对应 worktree | 在原环境核对并恢复活动 Run | 拷文件到任意路径即可迁移正在执行的进程 |

`.buildbeat/runtime/` 保存活动台账和原始日志，`.buildbeat/worktrees/` 保存工作树，通常均排除在 Git 之外。清理 runtime 后可依据 Git 面继续项目工作，但活动 Run 的精确恢复与原始日志不再保证。终态记录中的日志 digest 也不能还原日志正文。

跨地点接手时，先同步项目事实和候选，准备工具与环境，再决定从何处执行。BuildBeat 当前不提供活动 Run 的自动跨机器迁移。

## 怎样验证一次真实接力

选一个已有验证命令的小任务。会话 A 将目标与计划落盘并执行到可识别的状态；记录 Work、候选、验证结果与待批对象。关闭旧聊天，在不携带旧聊天历史的新会话 B 中只提供项目位置和接续请求。团队场景由另一位有权限的成员同步文件和候选后，用自己的工具执行这一步。

核对 B 是否能从文件和工具回读出同样的目标、状态与下一步，并在现有授权内继续。记录工具和模型版本、读取的文件、实际命令与最后结果。跨工具、跨成员或跨机器时，每种组合分别记录；演示对话不能替代这份证据。

现有 `tests/v2-resume.test.js`、`tests/v2-approval.test.js` 与 `tests/v2-overview-stages.test.js` 覆盖恢复和状态判断机制；它们不等于真实新会话接手的模型行为验收。
