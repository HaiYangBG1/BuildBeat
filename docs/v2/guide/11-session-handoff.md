# 跨会话接续

[English](11-session-handoff.en.md)

关闭旧会话前，将目标、决定、未验证范围和下一步写入项目；检查 Git、候选与运行状态。保留活动 Run 的台账和工作树。

新会话读取项目 AGENTS.md、Work 的 work.md（或旧 intent/plan）、决定与 status。能从记录查到的事实自行核对，沿用仍有效的授权；不把开新会话等同于重开 Run。

问一件事整体到哪了，用 `buildbeat status --repo . --all-repos --work <ID>`：工作说明或 result.md 里写了关系行（`- follows:`、`- split from:`、`- related:` 加工作编号）的工作，会被串成一条线，跨仓列出每项的阶段；反方向的关系自动推出，找不到的标为 `NOT_FOUND`。正文里只是提到的编号单列为 mentions 和 mentioned by，不算进这条线。手里只有任务、决策或合并请求编号时，用 `--ref <编号>` 找写了 `- ref: <编号>` 的工作。

接手一段代码时，先用 `buildbeat history --repo . --path <文件>[:<行>[-<行>]]` 查它来自哪项工作：运行时对这些行做 blame，再按三种确定的线索对上工作——提交落在某一轮运行记录的起点到候选之间、提交信息带 `Work: <ID>`、提交改动了 `delivery/work/<ID>/`；追不到的行单独计数，不按提交标题猜。读列出的 result.md 和 work.md 再动手。

开工前，或者接手一项写好一阵的工作时，先看 `buildbeat status --repo . --work <ID>` 里的 `facts:` 那块。"已核实的现状"的标题写了核实时的提交号、正文用反引号写了 `路径`、`路径:行` 或 `路径:起-止` 的，运行时会把这些代码和工作的起点对比：还没开跑的比当前 HEAD，开过跑的比最近一轮的起点。写了行号的只看这几行有没有被改，没写行号的看整个文件。改了的列为 changed，并附上改动它的提交；文件删了、对不上或对上多个文件的列为 not found。这些事实要重新核实，更新现状和标题里的提交号后重新接受。`accept` 和 `check` 遇到这种情况也会打印一行 `warning: facts …`，但不拦。已关窗的工作不比对：它的现状本来就是开工前的样子，做完后什么成立看 result.md。

已关窗的工作先读它的 result.md：做成了什么、定了什么、剩下什么转去了哪里、写进了项目哪些文档。起草新工作前，先在已关工作的 result.md 里搜相关的结论和遗留，把用得上的写进新 work.md 的"起因"。

主仓管理多个代码仓时，先运行 `buildbeat status --repo . --all-repos`。它只读查看主仓、主仓 `delivery/work/` 下 run 配置的 `repo:` 目标仓，以及主仓下一层含 `delivery/work/` 的 Git 仓，按真实路径去重，不递归。不存在或无效的目标、读不了的配置会给出警告，其余仓继续显示。

待人决定先列出，随后按仓显示未了结工作；CLOSED、CANCELLED 和已合并且配置没有 `release:` 的工作只计数，后者计为 `merged, not closed`，单仓 `status` 会提示它去收口。已合并但配有 `release:`、尚未关窗的工作仍显示。`--json` 返回 `{repos: [{repo, works, settled}], pending, warnings}`，包含已了结工作；`--work <ID>` 筛选各仓合并后的这项工作，`--run` 不能与 `--all-repos` 同用。

主仓配置指向的代码仓已有同名工作目录或运行台账时，状态、审查问题和决定取自代码仓，只在代码仓下显示；提示命令保留主仓配置，仓路径和配置路径相对当前目录，可填入人名、理由等占位内容后执行。目标仓还没有记录时，工作留在主仓并注明运行目标。不加 `--all-repos` 的主仓 `status` 也会读取这一层目标仓的真实状态，避免提示重复开跑。

换工具时重新配置命令、鉴权和输出合同；接手事实可以复用，具体工具执行能力需要验证。换人时同步候选、记录和权限，说明当前推进人及下一步。

换机器只能通过 Git 同步长期事实。活动进程、运行时文件、工作树和宿主资源不会随 clone 迁移，先核对原环境再选择接手方式。

跨会话演示不等于所有工具组合都已验证。
